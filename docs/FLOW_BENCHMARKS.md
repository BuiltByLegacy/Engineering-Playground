# Flow Lab Benchmark Program

This document defines how Flow Lab earns the right to show engineering-looking results without overstating the fidelity of the MVP.

## Validity tiers

Every displayed result belongs to one of three tiers.

### Tier 1 — Qualitative
Use for visual field behavior only.

Examples:
- flow accelerates through a restriction
- a blunt obstacle produces a wake
- smoother transitions reduce visible separation
- a longer or more obstructed path is less efficient

No dimensional claim is implied.

### Tier 2 — Semi-quantitative
Use for normalized trends that have passed deterministic regression checks.

Examples:
- design A has lower normalized loss than design B
- a geometry change reduces mean vorticity proxy
- outlet delivery improves by a normalized percentage

These may drive gameplay scores but are not certified engineering values.

### Tier 3 — Benchmarked quantitative reference
Use only for dimensional values generated by the classical reference model or for solver quantities that have been explicitly calibrated and benchmarked for the stated case.

Player-facing copy must identify these as **Reference estimates** unless a case-specific validation has been completed.

## Unity implementation boundary

The production game is Unity/C#.

- `Assets/Scripts/Flow/Simulation/D2Q9LbmSolver.cs` owns the CPU D2Q9 visual solver baseline.
- `Assets/Scripts/Flow/Engineering/FlowEngineeringReferenceModel.cs` owns classical dimensional equations.
- `Assets/Tests/EditMode/*` contains deterministic tests that should run through Unity Test Framework.
- Rendering, touch input, UI, particles, and future GPU acceleration are Unity concerns and must not be embedded into the numerical core.

The existing Godot implementation remains reference/prototype code during migration and is not the production runtime.

## Core reference-math checks

The following relationships are required and covered by deterministic unit tests:

1. Circular area: `A = pi D^2 / 4`
2. Rectangular hydraulic diameter: `D_h = 2ab / (a+b)`
3. Continuity: `Q = A V`
4. Mass flow: `m_dot = rho A V`
5. Dynamic pressure: `q = rho V^2 / 2`
6. Reynolds number: `Re = rho V D_h / mu`
7. Laminar Darcy friction factor: `f = 64/Re`
8. Turbulent Darcy friction factor: Haaland approximation
9. Darcy-Weisbach major loss: `DeltaP = f (L/D_h) rho V^2 / 2`
10. Minor loss: `DeltaP = K rho V^2 / 2`
11. Bernoulli no-loss pressure/velocity/elevation relationship

## D2Q9 guardrails

### Relaxation parameter
The single-relaxation-time BGK implementation requires:

`0 < omega < 2`

The solver rejects values outside that range.

### Low-Mach operation
For D2Q9 incompressible use, the game uses a conservative lattice Mach-number guardrail:

`Ma = U / c_s`

with

`c_s = 1/sqrt(3)`

Default target:

`Ma <= 0.10`

A case outside the guardrail is invalid for normal player-facing scoring until separately justified.

### Numerical finiteness
Density and velocity arrays must remain finite. NaN or infinity invalidates the run.

### Mass conservation
The benchmark harness records relative inlet/outlet mass-flux mismatch:

`epsilon_m = |m_out - m_in| / max(|m_in|, tiny)`

Initial educational target after a settled straight-channel run:

- preferred: <= 2%
- warning: > 2% and <= 5%
- invalid for scoring: > 5%

These values are acceptance targets, not claimed current measured results until executed in Unity.

## Canonical benchmark matrix

### B01 — Straight channel / developed profile
Purpose:
- basic stability
- no-slip wall behavior
- velocity-profile development
- mass conservation

Checks:
- solver remains finite
- centerline speed exceeds near-wall speed after settling
- profile is symmetric about channel centerline within tolerance
- inlet/outlet mass-flux mismatch recorded

Future quantitative extension:
- compare normalized velocity profile against plane-Poiseuille analytical shape
- report normalized RMSE

Initial target for educational fidelity after the profile benchmark is implemented:
- normalized profile RMSE <= 10% on production grid
- <= 15% on reduced mobile-quality grid

### B02 — Cylinder wake
Purpose:
- separation/wake behavior
- recirculation/vorticity response
- grid sensitivity

Checks:
- obstacle case produces more downstream vorticity than straight channel
- solution remains finite
- drag/loss proxy trend is monotonic with increasing blockage ratio in the tested range

The MVP does not claim vortex-shedding frequency or validated drag coefficient until a dedicated benchmark is added.

### B03 — Sudden contraction
Purpose:
- acceleration through reduced area
- pressure/loss trend

Checks:
- local velocity increases through contraction
- loss proxy increases as contraction becomes more severe
- dimensional reference card uses continuity + explicit K assumptions, not lattice-to-Pa conversion

### B04 — Sudden expansion
Purpose:
- recirculation and irreversible-loss intuition

Checks:
- expansion produces a recirculation region for sufficiently abrupt geometry
- vorticity/loss proxy increases versus a smooth diffuser of similar end areas

### B05 — Path-length trend
Purpose:
- verify engineering reference behavior

Checks:
- Darcy-Weisbach reference loss is linear with length when all other inputs are fixed
- gameplay scoring follows the same directionality

### B06 — Grid-resolution sensitivity
Run equivalent geometry at multiple grids, for example:
- 48 x 27
- 96 x 54
- 192 x 108 desktop/reference

Record:
- outlet-speed proxy
- mean-vorticity proxy
- mass-flux error
- execution time

No score threshold should depend on a grid-sensitive metric without quality-tier normalization.

### B07 — Relaxation/stability envelope
Sweep representative `omega` and inlet velocity combinations.

Record:
- finite/non-finite result
- mass-flux error
- maximum density excursion
- runtime

Use the results to define production-safe parameter ranges rather than exposing arbitrary solver tuning to content authors.

### B08 — Mobile performance
For target device classes record:
- grid size
- iterations/frame
- average and p95 simulation frame time
- thermal behavior during sustained play
- particle/visualization overhead separately from solver cost

The CPU solver is the correctness baseline. Production may later use Burst/Jobs or compute shaders, but accelerated implementations must match benchmark trends before replacing it.

## Scenario reference assumptions

Every applied scenario stores visible engineering assumptions separately from the visual solver.

### Plumbing
Reference model should define:
- fluid: water
- density and dynamic viscosity at stated approximate temperature
- nominal/internal diameter assumption
- path length
- roughness assumption
- fitting-loss K values or aggregate K

### HVAC
Reference model should define:
- fluid: air at stated approximate condition
- duct dimensions and hydraulic diameter
- branch/reference velocity or CFM target
- aggregate fitting-loss assumptions

True branch balancing requires independent branch flow measurements or a 1D network solver.

### Exhaust
Reference model may teach restriction and pressure-loss directionality using a clearly labeled simplified gas assumption.

Do not claim:
- exhaust pulse tuning
- scavenging
- acoustic prediction
- horsepower gain/loss
- catalyst/muffler thermal behavior

until an appropriate compressible/pulsating model exists.

### Manifold
Current 2D solver supports qualitative distribution and restriction visualization.

True outlet balance requires each outlet to have an independently measured mass/volume flow before a balance percentage is presented as quantitative.

## Test/report workflow

1. Unity EditMode tests run the reference math and CPU-solver regression suite.
2. Benchmark scene or automated runner executes longer settling/grid-sweep cases.
3. Results are exported to a machine-readable report.
4. Thresholds in challenge content are tuned only from benchmarked production solver settings.
5. Store copy and Learn-mode wording must use the validity tier associated with the displayed quantity.

## Definition of done for #15

Code foundation is complete when:
- classical equations exist in Unity C#
- deterministic tests exist
- CPU D2Q9 baseline exists in Unity C#
- solver guardrail tests exist
- benchmark matrix and validity tiers are documented

Validation is complete only after:
- tests are executed in the selected Unity project version
- benchmark results are captured on desktop and representative mobile hardware
- any failing numerical thresholds are tuned or fixed
- results are documented instead of assumed
